# Diagnostic locations and presentation

Diagnostic spans are half-open byte offsets into the original source. `start` and `end` remain authoritative for edits, identity, and source slicing. Presentation adds 1-based `line` and `col` values at the span's start without changing either byte offset or diagnostic ID.

Columns count Unicode scalar values, not bytes, grapheme clusters, terminal cells, or rendered escape characters. A valid multibyte rune occupies one source column; an offset inside that rune maps to its first byte's column. Each invalid UTF-8 byte occupies one column. Tabs count as one source column. A lone carriage return is source content. LF begins the next line, and CRLF is one line break: offsets at either CR or LF map to the preceding line's end position; the offset after LF starts the next line at column 1. EOF maps to the end of the last line, including the empty line after a final newline.

The protocol emits coordinates only when the invocation has captured the matching source unit and the complete span is valid: offsets must be nonnegative, ordered, and within the captured byte length. A zero-width primary span also needs explicit source-origin provenance, so a parser EOF location is distinguishable from a synthetic operational diagnostic at byte zero. Present cause and repair spans use their own unit when set, otherwise the diagnostic's unit. Nil nested spans remain absent. Source-less results retain their existing location-free projections.

The command session attaches the exact entry bytes already returned by checking the source tree. It does not reread the file or run another check to produce presentation. `WithPresentation` copies captured byte slices. Presentation context and source bodies are omitted from JSON and do not participate in diagnostic or result identity. JSON may include validated coordinates but never includes source snippets.

Human diagnostics retain the stable ID, code, optional unit and original `[start:end]` byte-range prefix, followed by an escaped file label with `line:column`, an escaped message, then a source excerpt and marker. The excerpt is one line: a multi-line range marks its first line and appends ` [continues]`. A zero-width insertion uses one `^`; a nonempty range uses `^` followed by `~` for the remaining rendered columns.

Source excerpts use printable ASCII. Printable bytes `0x20` through `0x7e` remain readable, backslash becomes `\\`, and source tabs expand to the next fixed four-column stop from the start of the line. Control bytes, DEL, and invalid UTF-8 bytes render as uppercase `\xHH`. Each non-ASCII Unicode scalar renders as uppercase `\u{HEX}`. These expansions define the rendered-column map used by the marker; they do not change wire coordinates. Filename and message fields use the same escapes, including `\x09`, `\x0A`, and `\x0D` for tab, newline, and carriage return, so untrusted text cannot add terminal control sequences or output lines.

Source excerpts, filenames, and messages are each bounded to 120 rendered ASCII columns. Excerpts crop around the primary start and use visible `...` omission markers, counting those markers inside the bound and never splitting an escape. Carets cover only visible source columns, not omission markers. Rendering does not query terminal width. Results without captured source keep the legacy human diagnostic line and omit the excerpt.
