## Summary

R1 has **three** independent defects, not two. All three must be fixed for the in-scope shapes to run end to end (reproduced and then fixed in a scratch prototype; all 10 witness shapes passed `check`, `build`, `app run`, interpreter/native agreement and `executionpeer.Validate` on both engines).

1. **CFG shape (checker).** A branch-free scalar body leaves its `OpReturn` in the entry block. corevalidate's two terminal-block rules disagree about the entry block: the structural rule exempts it (`corevalidate.go:2093`, `if block.PointID != function.EntryPointID`), the release-order rule does not (`corevalidate.go:4237`, `v.check(len(incoming) > 0, "core.release_order_indeterminate", block.ID)`). Every entry-returning scalar body therefore fails with `core.release_order_indeterminate`.
2. **Classifier (cgen).** `hasScalarOperations` (`cgen_program.go:2504`) recognises a scalar body only through `AddChecked/LessU64/EqualU64/RemainderU64/ScalarStore/Branch`. A body with only copy/const/write/return ops and blocks hits the foreign-call refusal at `cgen_program.go:686` (`native.build_failed ... multi-function foreign-call bodies are not supported`).
3. **Unused parameter (cgen, NOT in CONTEXT).** `emitProgramScalarFunction` (`cgen_program.go:2597`) never marks the entry parameter used. Any scalar body that does not read `n` fails clang under `-Werror,-Wunused-parameter` (`native.compile_failed ... unused parameter 'schway_scalar_0'`). Affects pure const (`let k = 7  k`), `write_newline()`-only, `write_text(...)`-only, and the constant-only overflow shape. Must be fixed without changing bytes for programs that do use the parameter (see Pitfall 2).

**Primary recommendation:** Lock D-27.2-03 option (a), the return-block split, in `checkScalarFunction` (5 lines). In cgen, extend `hasScalarOperations` with a structural clause (blocks present, U64-to-U64/Unit signature, all places U64/Bool, all ops in {Const, Copy, Return, WriteU64, WriteNewline, WriteText}, no Match/foreign contract/loan endpoints), and emit `(void)<param>;` in `emitProgramScalarFunction` only when no operation reads the parameter. No interp, executionpeer, corevalidate, originvalidate or session.go change is needed. Option (b) is rejected with evidence below.

## Decision: D-27.2-03 (return-block split chosen; blockless rejected)

### Option (a) return-block split: ACCEPTED

Prototype (verbatim; placed immediately after `b.lower(function.Body.Linear.Statements)` at `check/scalar.go:54`):

```go
if len(b.diagnostics) == 0 && b.current == 0 && !b.terminated(0) {
	e := b.blocks[0].ID
	r := b.newBlock("return")
	b.edge(e, r, "next")
}
```

Evidence per consumer `[VERIFIED: scratch run, prototype vs HEAD]`:

| Consumer | Result with the split | Evidence |
|----------|----------------------|----------|
| corevalidate | accepts; no code requires the entry to end in a branch | Ordinary `while` already emits `preheader -next-> condition` (`scalar.go:509`) and `if` emits `arm -next-> join` (`scalar.go:493,496`). The pattern string `"next"` is read by no peer: `grep '"next"'` over corevalidate, originvalidate, interp, executionpeer and cgen finds only producer sites in `check/scalar.go:493,496,509`. Consumers follow `Successors`/edges, not the pattern text. |
| originvalidate | accepts | `originScalarFixedPointWithFailure` only constrains `OpBranch` edges (`originvalidate.go` branch loop requires patterns `"true"`/`"false"`); `next` edges are unconstrained. |
| interp | executes | `interp.go` `runFrameStack`: a block with no terminator and exactly one successor falls through to `block.Successors[0]` (the `len(block.Successors) != 1` guard is the only precondition). |
| executionpeer | validates both engines' events | Its only CFG logic is `indexLoopOperations` (cyclic blocks); the split CFG is acyclic. |
| cgen | emits via the scalar emitter | `emitProgramScalarFunction` emits `goto <successor>` for an unterminated block with one successor (`cgen_program.go` end of the block loop). |

Why the trigger condition is exact: `b.current` becomes the join/exit block index (non-zero) after any `if`/`while`, so `b.current == 0 && !b.terminated(0)` is true **only** for bodies with no `if`/`while`. Every such body is currently refused (entry has no incoming edge), so no accepted program can change. This was confirmed empirically: across all 154 `.schway` files in the repo (92 accepted, 62 negative controls) HEAD and the prototype produce identical check results, identical core-document SHA-256, identical `cgen.EmitApplication` text and identical `cgen.EmitNative` text.

New block id: `newBlock("return")` yields `<fn>:block:return:1` with point `<fn>:point:block:1`. `ReturnPointID` is the unchanged `<fn>:point:return` string (`corevalidate.go:1134` only checks that string equality).

### Option (b) blockless form: REJECTED

Prototype: after lowering, set `Blocks`/`Edges` to empty slices when `b.current == 0 && !b.terminated(0)`. `[VERIFIED: scratch run]`

- check, corevalidate and originvalidate all accept it (`corevalidate.go:4352` `validateScalarFixedPoint` and `originvalidate.go` both contain an explicit `len(blocks) == 0` straight-line branch).
- cgen does **not**: bodies with `ScalarStore`/`AddChecked` reach `emitProgramScalarFunction`, which iterates `function.Linear.Blocks` (none) and emits `if (0) goto schway_block_-1;` -> `native.compile_failed: expected ';' after goto statement`. The ordinary emitter cannot take those ops. Fixing this needs a second, blockless scalar emission path in cgen, plus the interp `top.blocks == nil` path to stay in step.
- Blockless pure-copy bodies would ride the ordinary emitter while arithmetic bodies need a new scalar path, so the two halves of the in-scope set would take different routes and different peer classifiers.

Conclusion: (a) is smaller, reuses a shape every consumer already handles, and keeps one emission route. No concrete defect was found in (a).

### How each peer treats a pure copy/const body after the split `[VERIFIED: scratch run]`

`hasScalarCFG` is false for copy/const/return-only bodies, so corevalidate and originvalidate treat them as **ordinary linear** bodies with blocks (not scalar-CFG). They are accepted. This is sound for the shapes the scalar builder produces, with one fragility to record:

- On the ordinary path an `OpCopy` target must satisfy `v.targetMatches` (`corevalidate.go:4315` area): `TargetID == "<fn>:place:<opIndex+1>"`. The builder satisfies this for pure copy/const bodies only because every op creates exactly one place, in op order. Adding any write op flips `hasScalarCFG` to true and relaxes this to `scalarTargetMatches`. A future builder change that allocates a place without an op would make pure-copy bodies fail `core.invalid_target` while mixed bodies pass. Pin this with a long-chain witness (`let a = n; let b = a; let c = 5; let d = b; d` passed).
- The scalar fixed point (`validateScalarFixedPoint`) therefore does not run for pure copy/const bodies. That loses no information: no arithmetic or branch exists in them.

### The cgen rule (recommended; verified)

Extend `hasScalarOperations` so all four call sites (`cgen_program.go:686, 871, 949, 2347`) agree. Add, before the existing op loop:

```go
if function.Match == nil && len(function.Linear.Blocks) > 0 && function.ForeignContract == nil &&
	len(function.Linear.LoanEndpoints) == 0 && function.Parameter.Type == "U64" &&
	(function.ReturnType == "U64" || function.ReturnType == "Unit") {
	allScalar := true
	for _, place := range function.Linear.Places {
		c := placesTypeName(function.Linear, place.TypeID)
		if c != "U64" && c != "Bool" {
			allScalar = false
		}
	}
	for _, operation := range function.Linear.Operations {
		switch operation.Kind {
		case core.OpConst, core.OpCopy, core.OpReturn, core.OpWriteU64, core.OpWriteNewline, core.OpWriteText:
		default:
			allScalar = false
		}
	}
	if allScalar {
		return true
	}
}
```

Why each guard matters:

- `len(Blocks) > 0` is **load-bearing**: write ops are legal in blockless hand-built core programs and are served by the ordinary emitter (`cgen_program.go:2388-2400` handles `OpWriteU64/Newline/Text`). Dropping the guard (for example by only adding the three write ops to the existing op loop) would reroute blockless write bodies into the scalar emitter, which cannot emit them, and would change bytes.
- All places U64/Bool and ops in the six-op set exclude `OpMove`, `OpBorrow*`, `OpForeignCall`, `OpRelease`, `OpCall`, `OpFail`, `OpDefect`, payload ops and every Owner/Resource/Loan place.
- `Match == nil`, `ForeignContract == nil`, `LoanEndpoints == 0` and the signature check are belt-and-braces for producers other than the scalar builder.

Verified with this exact clause: cgen, native, core, check, corevalidate, originvalidate, interp, executionpeer and syntax package tests pass; the full `internal/compiler/session` and `cmd/schway` packages passed (79s) with the looser first draft, and the focused Phase 26/27 session tests pass with the tightened version.

### The unused-parameter fix (third defect)

In `emitProgramScalarFunction`, right after the function prologue line:

```go
parameterUsed := false
for _, op := range function.Linear.Operations {
	if op.SourceID == parameter.ID || op.RightID == parameter.ID {
		parameterUsed = true
	}
}
if !parameterUsed {
	fmt.Fprintf(out, "  (void)%s;\n", locals[parameter.ID])
}
```

It must be **conditional**. An unconditional `(void)` would change the emitted C of every existing accepted scalar program and break D-27.2-05. (The ordinary emitter has an analogous latent defect, `(void)param` only when an `OpConst` exists at `cgen_program.go:2381-2386`; it is unreachable from the scalar builder once the split lands, so leave it alone.)

## Parser interaction (question 3)

`scalarBodyStart` (`syntax/parser.go:~318`) routes a body to `scalarLinearBody` when it starts with `var`/`if`/`while`, with a write call, or with a scalar-shaped `let` (`scalarLetStart`: `let IDENT = (NUMBER|IDENT) [op operand]`, not followed by `(` or `.`, only when parameter is U64 and return is U64/Unit).

**Finding (not in CONTEXT, outside R1): a second a671308 regression.** Only the *first* `let` is inspected. `fn main(n: U64) -> U64 { let a = n  let b = helper(a)  b }` passed `check` at a671308~1 and fails at HEAD with `syntax.expected_linear_result` + `syntax.expected_rbrace` (reproduced: HEAD fails, a671308~1 passes). A body whose first `let` is a call (`let b = helper(n)  b`) is unaffected (routes to the linear parser at both commits). This is a mixed scalar-then-call `let` body: a ownership/call shape misrouted into the scalar grammar.

- Evidence that nothing in the repo exercises it: all 154 `.schway` files give identical check results at HEAD and with the fix; the only differences between HEAD and a671308~1 across the corpus are `examples/sum_to_n.schway` and `examples/fizzbuzz.schway`, which need scalar `let` inside loops and so are the intended a671308 gain.
- Scope call needed from the user/planner (Open Question 1). Recommendation: **do not fix inside 27.2** (the fix would be parser lookahead over all top-level lets, which is new routing logic outside "restore branch-free scalar bodies" and outside D-27.2-02's scalar-builder scope); instead add a characterization test (HEAD behaviour, `syntax.expected_linear_result`) and record it in the `26-VERIFICATION.md` addendum (D-27.2-09) as newly found debt R1b so it is not lost.

`var`-led, `if`-led and `while`-led bodies were already scalar-routed before a671308 and are untouched by it.

## Common Pitfalls

### Pitfall 1: The "unreachable trailing result" control has a different code than CONTEXT states
At HEAD (and with the fix) both-arms-`defect` then trailing result gives `core.terminal_block_unreachable` on the `if-join` block, not `core.release_order_indeterminate`. Pin the observed code. `[VERIFIED: scratch run]`

### Pitfall 2: Byte identity is broken by anything unconditional
Any new text emitted for all scalar functions (e.g. an unconditional `(void)param`) changes existing C. Gate on the new condition only.

### Pitfall 3: "Overflowing +" is a runtime defect, not a check refusal
`check` has never refused it statically. At HEAD a straight-line overflow body is refused only as a side effect of R1 (`core.release_order_indeterminate`). After the fix it must **check, build and fail at runtime**: interpreter `Outcome.Kind == execution.OutcomeDefect` with event `Output == "U64 addition overflow"`; native exit 65, stdout empty, stderr exactly `schway: U64 addition overflow\n`. Treat this control as red-to-green, not an unchanged refusal. Its witness must also read no `n` (constant-only), so it doubles as the unused-parameter regression.

### Pitfall 4: Phase 16 public-emitter inventory scans test files

## Byte-identity guard (question 4)

Existing infrastructure: no golden for core documents or emitted C over `examples/` exists; `scripts/check-phase27-receipts.sh:45-46` pins only source and fixture hashes of `fizzbuzz.schway`, `sum_to_n.schway`, `fizzbuzz-15.out`, `fizzbuzz-1000.out` (unchanged by this phase automatically since the files are not edited).

Recommended cheapest robust guard:

1. Wave 0 (before any source change): add `TestPhase272AcceptedCorpusByteIdentity` in `internal/compiler/session/` that walks `*.schway` under `examples/` and `testdata/`, runs `session.Check`, and for accepted files compares core-JSON SHA-256 and `cgen.EmitApplication` SHA-256 with a committed golden `testdata/phase272/accepted-corpus-hashes.json` (relative path, sorted, plus a count floor so the walk cannot go inert). Generate the golden at HEAD via a small `-update`-style env switch local to the test, commit golden + test, confirm green, then land the fix and confirm still green.
2. Use only `cgen.EmitApplication` (Pitfall 4). `EmitNative` goes through the same `emitProgramScalarFunction` with a different shell; it is covered by the unchanged cgen/native package tests and by the scratch measurement, or add inventory rows deliberately.
3. Add a checker-level structural assertion in `internal/compiler/check/check_test.go`: for a branch-free body the function has exactly two blocks (`entry`, `return:1`) joined by one `next` edge; for sum_to_n-style `if`/`while` bodies the block/edge counts are unchanged (this is the "fix never fires for accepted programs" condition).
