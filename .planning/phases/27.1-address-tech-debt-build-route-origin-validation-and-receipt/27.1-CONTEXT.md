# Phase 27.1: Address tech debt: build-route origin validation and receipt-gate docs - Context

**Gathered:** 2026-10-10
**Status:** Ready for planning

<domain>
## Phase Boundary

Close the two M005 audit findings that weaken shipped assurance without changing
any accepted program's behavior:

- **F1** — the public application admission routes `schway build`
  (`session.BuildApplication`) and `schway app verify`
  (`session.VerifyApplicationCases`) run the checker and `corevalidate` but never
  `originvalidate.ValidatePublished`, while `RunInterpreterApplication`,
  `check`, `interface export` and the `run` command all apply the origin peer.
  Reproduced: `testdata/phase25/shared_copy_accept.schway` is refused by
  `schway check` with `core.origin_omitted` but `schway build` writes an artifact.
  Pre-existing since Phase 22, not an M005 regression.
- **F2** — the Phase 27 clean-checkout guide documents a receipt-gate command
  that fails closed (`wrong_revision`) at any HEAD after the evidence revision,
  because the gate defaults to `git rev-parse HEAD` and the guide never mentions
  `PHASE27_EXPECTED_REVISION`.

Plus a small set of behavior-neutral audit-record fixes (D-27.1-09). No new
language capability, no change to emitted C for accepted programs, no change to
example sources or fixtures (their hashes are pinned by committed receipts).
</domain>

<decisions>
## Implementation Decisions

### Application admission shape (F1)
- **D-27.1-01:** Extract one unexported application-admission helper in
  `internal/compiler/session` (name at planner discretion, e.g.
  `admitPublishedApplication`): given an accepted `CheckResult`, run
  `corevalidate.Validate`, then `originvalidate.ValidatePublished` on the
  peer-normalized `validated.Program()` (same order as `CheckCommandFile` and
  `InterfaceExportCommandFile`), and return the admitted program. Use it from
  all three public application routes: `BuildApplication`,
  `RunInterpreterApplication`, and `VerifyApplicationCases`. Rationale: F1 exists
  because each route hand-copies admission; one helper makes skipping a peer a
  structural impossibility rather than a review catch. D-27-07's "copy over dep"
  preference is about dependencies and does not argue for re-copying in-package
  code. — **Reversibility:** reversible — single package, unexported.
- **D-27.1-02:** Do **not** route `runNative`, `RunInterpreter`, or
  `RunNativeCommandFile` through the helper. They deliberately do not gate on
  origin (differential/verify-corpus lanes intentionally run
  undeclared-borrow-derived-return fixtures such as
  `TestExclusiveBorrowInterpreterNative`; the `run` command gates at the
  command-file layer via `publishedOriginProblemFile`). The helper's doc comment
  must say it is the *application/publication* gate and point at the
  `publishedOriginProblemFile` rationale so nobody later widens it.
- **D-27.1-03:** Origin admission runs immediately after `corevalidate` and
  before `callgraph.EntryFunction`, entry-shape checks,
  `pathoracle.ValidateLocalOwnerPaths`, manifest resolution,
  `cgen.EmitApplication`, and any clang invocation or file write. A refused
  program leaves no artifact and no `<out>.schway-build.json` sidecar.
- **D-27.1-04:** Refusal surface, per route, preserving each route's existing
  contract:
  - `BuildApplication` returns the origin refusal as a **diagnostic** (the same
    `originPeerRefusalDiagnostic` that `check` emits, with the origin code and a
    source span when available), so `runBuild` reports
    `protocol.StatusInvalid` with the origin code — consistent with
    `schway check` and correctly classed as a user-fixable source problem, not
    an operational `native.build_failed`.
  - `RunInterpreterApplication` keeps its existing byte-identical error
    `origin validation failed: <code>`.
  - `VerifyApplicationCases` follows its existing error style (planner chooses
    exact wording; it must name the origin code).
  - Existing `corevalidate` failure strings/statuses are unchanged (moving them
    to diagnostics is deferred debt, not part of F1).
  — **Reversibility:** costly — the `build` refusal status/code becomes part of
  the public CLI JSON contract.
- **D-27.1-05:** No currently buildable shipped program may be newly refused.
  Researcher evidence: `schway check` (which already runs the origin peer)
  passes `examples/sum_to_n.schway`, `examples/fizzbuzz.schway`,
  `examples/phase22/identity.schway` (local-owner app), `phase23/file_byte`,
  `phase24/error`, `phase24/transfer`, `phase26/checked_add_overflow`. The
  plan must keep these building (positive controls) and emitted C for accepted
  programs byte-identical.

### Receipt-gate default (F2)
- **D-27.1-06:** Docs fix; **keep the gate's fail-closed HEAD default
  unchanged**. The revision check binds a receipt to the exact compiler/driver
  commit, which the four recomputed hashes (two sources, two fixtures) cannot
  see; loosening to an ancestor rule would let old receipts vouch for a changed
  compiler and break on shallow CI checkouts. Reject-reason names stay
  unchanged.
- **D-27.1-07:** `examples/phase27/README.md` documents two explicitly labeled
  uses, keeping command truth in the guide (D-27-06):
  1. *Fresh CI artifacts at their commit* — artifact name
     `phase27-receipt-<os>-<sha>` carries the commit; check out that `<sha>`;
     save each host's whole downloaded log as `host-macos.receipt` /
     `host-linux.receipt` (replace the confusing "save one result row per
     host"); run the bare command; mismatched checkout fails `wrong_revision`.
  2. *Re-checking the committed Phase 27 receipts from a later checkout* —
     `PHASE27_EXPECTED_REVISION=6224f8b2c9c15f54270a232fab2bce12628c7f19 sh scripts/check-phase27-receipts.sh .planning/phases/27-exact-fizzbuzz-and-cross-host-evidence/host-macos.receipt .planning/phases/27-exact-fizzbuzz-and-cross-host-evidence/host-linux.receipt`.
     State that this attests the historical revision, not the current HEAD;
     that it passes only while the four declared inputs are unchanged
     (otherwise `source_hash_mismatch`/`fixture_hash_mismatch`, correctly); and
     that the gate checks consistency, not authenticity (anchor: run record in
     `27-HOST-EVIDENCE.md`).
  Also note the script `cd`s to the repo root, so relative log paths resolve
  from the root — run from the root or pass absolute paths.
- **D-27.1-08:** Add a one-line stderr hint on the `wrong_revision` /
  `result_revision_mismatch` rejects (expected vs got, and the
  `PHASE27_EXPECTED_REVISION` override) without changing reason names or
  exit status. Extend `TestPhase27GuideContract`
  (`internal/compiler/session/session_phase27_docs_test.go`) to require the
  override, `wrong_revision`, the pinned revision and the committed receipt
  paths, and to **execute** the documented pinned command against the committed
  receipts and require `status=pass` (execution, not inspection; needs no
  clang).

### Proof and re-evidence bar
- **D-27.1-12:** Reached control without seams:
  `testdata/phase25/shared_copy_accept.schway`. A focused session test (e.g.
  `TestPhase271BuildApplicationRefusesOriginUnpublishable`) first asserts the
  control is reached (checker clean, `corevalidate` valid, linear U64 entry,
  `ValidatePublished` → `core.origin_omitted`), then asserts `BuildApplication`
  returns the origin diagnostic using a runner with a nonexistent clang path
  (proves refusal precedes emission/clang) and that the temp output dir stays
  empty. Add a `cmd/schway` test: `schway build` on that fixture exits with the
  invalid status, reports the origin code, and leaves no artifact or sidecar.
- **D-27.1-13:** Behavior-level route-parity test (e.g.
  `TestApplicationRoutesApplySameAdmissionLayers`) driving the same rejected
  sources (a checker reject, the origin-unpublishable fixture, a corevalidate
  reject if cheaply available) through `BuildApplication`,
  `RunInterpreterApplication`, and `VerifyApplicationCases`; every route refuses

  must not imply `RunNative`/`RunInterpreter` gate. No source-grep tests.
- **D-27.1-14:** Record red→green: run the focused tests before the fix (fail:
  build succeeds and writes an artifact) and after (pass). Also run focused
  local-owner/build tests to catch newly refused legitimate builds
  (e.g. `go test ./internal/compiler/session ./cmd/schway -run 'Build|Phase22|Phase24|Phase25|Phase271' -count=1`).
  Full suite stays hosted-only.
- **D-27.1-15:** One fresh hosted `ci.yml` `workflow_dispatch` (default inputs;
  no `phase26_focused`, no `record_validation_corpus`) at the final 27.1 SHA,
  both host lanes, with no pushes during the run. Record run ID/URL/SHA,
  per-job conclusions and the fresh two-host Phase 27 receipts (gate run pinned

  `26-VERIFICATION.md` and `27-VERIFICATION.md` noting 27.1 changed
  `session.go` after 6224f8b and citing the new run. Do not edit the body of
  `27-HOST-EVIDENCE.md` or the committed 6224f8b receipts. No re-run of the
  Phase 26/27 verifier agents; keep 27.1 validation proportionate.
- **D-27.1-16:** Allowed claims: the three application routes apply checker →
  corevalidate → origin peer before entry analysis/emission; reached control
  refused via API and CLI with no artifact (red/green cited); examples still
  build and match (hosted run cited); documented gate command passes against
  committed receipts. Forbidden claims: artifacts "verified"/"origin-checked"
  (admission is of source); all routes uniform; F3–F5 addressed; Phase 27
  receipts regenerated (unless they were); unchanged fixture hashes prove Phase
  27 currency; receipt authenticity; local focused runs as hosted evidence;
  retroactive checking of previously built artifacts; mutation testing beyond
  the single red/green.

<code_context>
## Existing Code Insights

### Reusable Assets
- `originPeerRefusalDiagnostic` — source-attributed origin refusal already used by `check`; reuse for `build`.
- `knownAdmissionDivergences` table — existing pin that the control fixture is a checker/corevalidate-accept, origin-reject divergence.
- `TestPhase27GuideContract` — existing guide contract; extend rather than add a new docs test.

### Established Patterns
- Admission order: checker → `corevalidate` → `originvalidate.ValidatePublished` on the peer-normalized program (`CheckCommandFile`, `InterfaceExportCommandFile`).
- Internal execution lanes (`runNative`, `RunInterpreter`) intentionally ungated on origin; gating lives at public command/application layers.
- Receipt gate checks consistency not authenticity; hosted run record is the authenticity anchor.
- Full suites run only in hosted CI; focused `go test -run` locally is fine.

### Integration Points
- `runBuild` already maps returned diagnostics to `StatusInvalid`, so returning diagnostics from `BuildApplication` needs no CLI change.
- `BuildApplication` has no non-CLI callers in `session`; native tests call `native.BuildApplication` directly.
</code_context>

User preference carried forward: "another copy and paste is better than another dep" — no new dependencies.
