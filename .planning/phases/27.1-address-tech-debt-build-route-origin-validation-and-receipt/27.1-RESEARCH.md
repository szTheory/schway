### Pattern 1: Helper returning a layered refusal (recommended signature)

Routes disagree on how they spell a corevalidate refusal, so the helper must NOT format strings; it returns structured data and each route formats. Current spellings [VERIFIED: session.go:1149-1155, 1387-1393, session_app_verify.go:221-224]:

- `BuildApplication` / `RunInterpreterApplication`: `errors.New("core validation failed without a named problem")` when `len(Problems)==0`, else `fmt.Errorf("core validation failed: %s", Problems[0].Code)`.
- `VerifyApplicationCases`: `errors.New("source core validation failed")` (no code), returned as `return report, err`.


## Common Pitfalls

### Pitfall 1: Red run must use a real clang, not the nonexistent-clang runner
**What goes wrong:** With `native.Runner{ClangPath: missing}`, pre-fix `BuildApplication` on the control does NOT succeed: `runner.BuildApplication` does `os.MkdirAll(outputDirectory)` (native_app.go:153) then `exec.LookPath` (:161) and returns `&ToolError{Code:"native.tool_missing"}`. That is still red (error instead of diagnostics) but it is not the "build succeeds and writes an artifact" red that D-27.1-14 describes.
**How to avoid:** Record red evidence from (a) the `cmd/schway` test with the real runner (pre-fix: exit 0 and artifact + `.schway-build.json` exist) and (b) the session test (pre-fix: `err` is `native.tool_missing`, no diagnostics). Both fail pre-fix, both pass post-fix. Put the output dir inside an existing `t.TempDir()` and assert `os.ReadDir` is empty after refusal (pre-fix with a missing clang the directory may be created; for a pre-existing temp dir it is simply left empty, so assert on the artifact path and sidecar path not existing as well as emptiness).
**Warning signs:** a red run whose failure message mentions `tool_missing` only.

### Pitfall 4: Hint text and existing gate tests
`TestPhase27HostReceiptGate` asserts rejected output contains `status=fail`, contains the reason substring, and does NOT contain `status=pass` (session_phase27_host_test.go:141-148). The hint line must not contain `status=pass`. Print it on stderr before/after the existing `reject` line; do not change `reject` format `phase27 receipt gate: status=fail reason=%s`.

### Pitfall 5: `${PHASE27_EXPECTED_REVISION:-$(git rev-parse HEAD)}`
The command substitution is only evaluated when the variable is unset, so the pinned run does not need a git HEAD; but `hash_list` still needs `git hash-object` (works outside a repo too). CI has `fetch-depth: 0` anyway.

### Pitfall 6: Guide-contract execution is intentionally brittle to input changes
The executed pinned command passes only while the four declared inputs (two sources, two fixtures) hash as at 6224f8b. A future `format` reformat of `examples/fizzbuzz.schway` would flip `TestPhase27GuideContract` red with `source_hash_mismatch`. This is correct behavior (D-27.1-07); make the Go failure message say so and point at D-27.1-10's "bundle with re-evidence run" deferral.

### Pitfall 7: Test names collide with Phase 27 focused regexes
`TestPhase271...` matches `^TestPhase27` (the guide's focused commands `go test ./internal/compiler/session -run '^TestPhase27'` and `./cmd/schway -run '^TestPhase27'`). Harmless (the new tests pass without clang for the refusal paths), but note that the Phase 27 guide's "focused controls" would then also run them. CONTEXT's names and the D-27.1-14 regex `Phase271` are fine; just be aware. Do not touch the `verify-phase27.sh` control test names.

### Pitfall 8: `VerifyApplicationCasesFile` still writes a report on refusal
`VerifyApplicationCasesFile` calls `VerifyApplicationCases`, then `writeApplicationVerificationReport(reportPath, report)` unconditionally, then returns `verifyErr` (session_app_verify.go:188-192). So an origin refusal leaves a `status: fail` report (zero cases, empty `EmittedCDigest`, `Verified=false`) and the CLI prints `schway app verify: <err>` with exit 3 (`exitOperational`, main.go:303-307). That is the existing checker-refusal behavior; keep it. Consequence: the parity test cannot assert "no file written" for verify; assert instead `report.Verified == false`, `report.EmittedCDigest == ""`, `len(report.Cases)==0`, error names the code. Accepted asymmetry: build refuses with exit 2 (invalid), verify with exit 3. Do not claim uniform CLI status (D-27.1-16 forbids "all routes uniform").

### Pitfall 9: Concurrency group cancels the hosted run
`ci.yml` has `concurrency: group: ci-${{ github.ref }}, cancel-in-progress: true`. Any push to `phase26-validation` during the dispatched run cancels it. Also the branch is currently 8 commits ahead of `origin/phase26-validation` (git status), and pushing needs explicit user authorization.

### Pitfall 10: Doc-only commits after the dispatched SHA
Receipts bind to `git rev-parse HEAD` at dispatch. The evidence write-up commits that follow are `.planning/`-only, which is fine (same pattern as Phase 27) because the gate for the fresh receipts is run with `PHASE27_EXPECTED_REVISION=<dispatch sha>` and the README documents exactly that use. Do not commit anything to non-planning paths between dispatch and download.
