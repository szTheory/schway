    Build the substitution mechanism. It must require ZERO changes to the driver: the driver
    keeps spawning "the binary at `--lang`" and reading its stdout, and never learns it is
    not talking to the real `lang`.

    Mechanism: a tiny test-only stand-in program, built into a `t.TempDir()` by the test,
    whose entire behaviour is to write a fixture file's bytes to stdout and exit with a
    fixed code. The test passes that stand-in's path as `--lang`. Because the driver's code
    path is unchanged, the import-boundary lint (06-13) remains trivially satisfied and there
    is no second, untested driver branch to maintain.

    Capture the real output first: run the real `lang --json check` on an injected held-out
    fixture, write its stdout to `cmd/lang-repair/testdata/` as the baseline capture, and
    assert the capture is non-empty and contains at least one driver-eligible repair. A
    capture that contains no eligible repair would make both guards vacuous, so refuse it.

    Add `func mutateCapture(raw []byte, mode string) ([]byte, error)` in the test file,
    decoding the captured JSON into a generic map, applying the requested mutation, and
    re-marshalling. Two modes to start: `identity` (no change) and a validation mode that
    asserts the round-trip is byte-stable, so a later scramble can be attributed to the
    scramble rather than to the re-marshal.

    Tracer: real capture -> `identity` mutation -> stand-in subprocess -> driver -> the same
    repair outcome as running against the real binary. End to end, proving the substitution
    is faithful before any guard depends on it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stand-in subprocess stdout -> driver | The substitution seam; the driver must not be able to distinguish it from the real binary |
| mutated capture fixtures -> guard verdict | A malformed mutation would make a guard pass or fail for the wrong reason |
| driver-produced files -> in-process fallback oracle | The only place the reducer may be reached, after the driver has exited |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-06-THEATER-02 | Spoofing | a guard that can only ever assert green, and so cannot detect its own inertness | high | mitigate | `TestVocabularyRemovalGuardIsNotInert` (green control) and `TestProseScrambleFixtureKeepsStructuredFieldsIntact` (bidirectional scrambler verification) |
