    - Test 3: changing `Lane.ID` changes the `Result.ID`; changing `Lane.Status` changes the `Result.ID` (proves the test is not inert).

  <action>
    Add `TestMetricsAndLaneFieldsExcludedFromIdentity` and
    `TestIdentityFieldEnumerationIsExhaustive` to
    `internal/compiler/protocol/protocol_test.go`.

    `TestMetricsAndLaneFieldsExcludedFromIdentity` builds a `protocol.Result` via
    `protocol.New("verify", protocol.StatusPass)`, records `Finalize().ID`, then uses
    `reflect` to set every settable field of `result.Metrics` to a non-zero sentinel
    (int/int64 -> 7, string -> "sentinel") and asserts `Finalize().ID` is unchanged. It
    repeats this for a single `protocol.Lane` appended to `result.Lanes`, skipping only
    the fields named `ID` and `Status`. It then positively asserts that changing `Lane.ID`
    and separately changing `Lane.Status` each DO change `Result.ID` — without those two
    positive assertions the test could pass while `Finalize` ignored lanes entirely.

    `TestIdentityFieldEnumerationIsExhaustive` reflects over `protocol.Metrics` and
    `protocol.Lane` and compares the sorted field-name slices against two literal expected
    slices declared in the test body. Its failure message must instruct the reader to add
    the new field to the sentinel loop above and re-confirm it is identity-excluded. This
    is the self-invalidating half: it is what makes the exclusion test keep holding once
    06-06 adds `cache_status`, `selection_reason`, `machine_id`, `gate_verdict`,
    `cold_or_warm`, `stage_breakdown`, and `cache_inputs_reused_count`.
