<objective>
Grow `diagnostic.Repair` from a classification into an applicable edit — additively, on the
already-shipped `lang.diagnostic/1`, with the identity split held exactly where it is.

Purpose: DX-04's driver cannot apply anything today. `Repair` is `{kind, detail}`: no span,
no replacement text. This is the minimal additive extension that makes a repair mechanically
applicable, borrowing rustc's `Applicability` enum and rustfix's discipline (D-06-24).
Output: three new optional fields, a closed applicability vocabulary, and an executable
proof that a coordinate shift cannot move a diagnostic ID.
</objective>

<task type="checkpoint:decision">
  <name>Task 0: Ratify the identity-bearing split for the extended Repair fields</name>
  <reversibility rating="one-way">D-06-24. The identity-bearing / non-identity-bearing split is a published contract. Moving `span`, `replacement`, or `applicability` across that line later changes every previously-published diagnostic ID — every recorded evidence reference, every pinned test digest, every agent workflow keyed on a diagnostic ID.</reversibility>
  <decision>
    Confirm D-06-24's split as written before the fields exist (expected: yes, it is locked).

    `diagnostic.Repair` gains three optional fields on the already-shipped
    `lang.diagnostic/1`:
    - `span` (optional pointer to the existing `Span` type),
    - `replacement` (optional string),
    - `applicability`, an ENUM with exactly `MachineApplicable`, `RequiresConfirmation`,
      `Unspecified` — deliberately not a boolean, because only `MachineApplicable` is
      driver-eligible and everything else routes to the recorded non-gating exercise.

    **All three join `detail` in the NON-identity-bearing bucket. Only `kind` participates
    in semantic identity.** The existing `ErrorWithRepairs` already derives `RepairKinds`
    from `repair.Kind` alone; that derivation must not change. The reason is concrete: if
    `span` were identity-bearing, editing a line above a diagnostic would shift its
    coordinates and spuriously change its ID, breaking every pinned digest in the tree.

    `lang.diagnostic/0` bytes remain frozen. `Schema1 = "lang.diagnostic/1"` already exists
    and is the frozen additive version — no new schema constant is minted, and this is a
    DIFFERENT schema from 06-06's coordinated `lang.command`/`lang.verify-lane` bump.

    Also confirm: the canonical repair sort in `ErrorWithRepairs` (by `Kind`, then `Detail`)
    stays keyed on those two fields only. Adding `Span`/`Replacement` to the sort key would
    change the emitted repair ORDER for existing diagnostics, which is observable output
    even though it is not identity.
  </decision>
  <options>
    - **Accept as written (recommended):** three optional non-identity-bearing fields, `kind` remains the sole identity contributor, sort key unchanged.
    - **Make `replacement` identity-bearing:** would let two different suggested fixes for the same defect be distinguishable by ID, at the cost of making every diagnostic ID sensitive to prose-adjacent edit text. Irreversible once published.
    - **Boolean `machine_applicable` instead of an enum:** simpler, and collapses `RequiresConfirmation` into `false`, losing the routing distinction D-06-24 needs between driver-eligible and exercise-only repairs.
  </options>
  <recommendation>Accept as written. The identity split is the part that cannot be revised after the first `/1` diagnostic carrying a span is published.</recommendation>
  <blocking>true</blocking>
  <resume-signal>Developer confirms D-06-24's identity split and the unchanged sort key. Then proceed to Task 1 and extend `diagnostic.Repair` with the three non-identity-bearing fields.</resume-signal>
</task>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `replacement` text -> a source file the driver will edit | The repair driver acts on this string; it is compiler-produced, and the binary is the trust boundary producing it |
| identity-bearing field set -> every published diagnostic ID | The one-way seam |
| `applicability` value -> driver eligibility | A fail-open default here would let an unverified edit be applied mechanically |

| T-06-REPAIR-01 | Tampering | a coordinate shift changing a published diagnostic ID | high | mitigate | `span`/`replacement`/`applicability` excluded from `repairKinds`; `TestRepairSpanShiftDoesNotChangeDiagnosticID` plus the reflection enumeration guard |
| T-06-REPAIR-02 | Elevation of Privilege | an incomplete or defaulted repair being applied mechanically | high | mitigate | `DriverEligible` requires `MachineApplicable` AND a span AND a replacement; empty applicability normalizes to `Unspecified`, never to `MachineApplicable` |
