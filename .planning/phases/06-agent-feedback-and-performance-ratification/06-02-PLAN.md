  <name>Task 0: Ratify the net-new /0 schema mint and the explain/query command arity</name>
  <reversibility rating="one-way">D-06-04 mints published versioned product-API schemas; per the standing project rule `/0` bytes freeze on ship and can only be superseded additively by a `/1`. There is no un-publishing.</reversibility>
  <decision>
    Two items, both blocking Task 1.

    **(a) Confirm D-06-04 as written (expected: yes, it is locked).** `explain` and `query`
    are net-new documents and get net-new `lang.explain/0` and `lang.query/0` schemas, each
    with a content-derived `id` following the existing `Finalize()` pattern. They are NOT
    crammed into `lang.command/0`, and they do NOT require the `lang.command/0` -> `/1`
    bump on their own account (D-06-31). Rule established here: a new capability gets a new
    `/0` schema; only extending an existing document's fields earns a `/1` bump.

    **(b) Resolve an under-specification in D-06-05, which the planner must not decide
    alone.** D-06-05's concrete grammar is `lang explain <id> [--depth=N] [--json]` and
    `lang query <id-or-pattern> [--kind=...] [--depth=N] [--cursor=C] [--json]` — neither
    names a source operand. But D-06-02 forbids any persisted graph, store, or daemon, so
    there is no state a bare `<id>` could be resolved against: the compiler must re-derive
    the diagnostic from source on every cold invocation. The in-tree precedent that already
    does exactly this is `lang debug-map SRC [QUERY]`.

    Proposed resolution (recommend accepting): the shipped grammar is
    `lang explain SRC ID [--depth=N] [--json]` and
    `lang query SRC ID_OR_PATTERN [--kind=K] [--depth=N] [--cursor=C] [--json]`,
    matching `debug-map SRC QUERY` exactly. D-06-05's `<id>` is read as the addressing
    argument, with the source operand implied by the project's existing CLI convention.
    The addressing grammar itself (which ID vocabularies are recognized, and their prefixes)
    is unchanged from D-06-01 and is NOT re-opened here.

    This matters because D-06-01 is rated `costly`: the addressing grammar is a published
    agent-facing contract, and changing the operand list later invalidates every agent
    workflow built on it.
  </decision>
  <options>
    - **Accept as proposed:** `lang explain SRC ID`, `lang query SRC ID_OR_PATTERN`, following `debug-map SRC QUERY`. Consistent with every other command in the tree.
    - **Bare-ID grammar as literally written in D-06-05:** requires a persisted diagnostic store or a daemon, both of which D-06-02 and PROJECT.md forbid for M001. Not implementable this milestone.
    - **Source via a flag** (`lang explain <id> --source=SRC`): honors the positional grammar literally but introduces a flag shape no other command in the tree uses.
  </options>
  <recommendation>Accept as proposed. It is the only option implementable under D-06-02's no-persistence constraint that also matches shipped CLI convention.</recommendation>
  <blocking>true</blocking>
  <resume-signal>Developer confirms D-06-04 and selects one of the three command-arity options. Record the chosen grammar in the plan summary, then proceed to Task 1 and mint `lang.explain/0` with that operand list.</resume-signal>
