  - `TestPayloadLayoutMutationRefused` (D-12-37) — a committed frozen fixture with

  - `TestPayloadSlotSwapMutationKilled` (D-12-38) — the DECISIVE control. It seeds a
    real, type-safe bug in `cgen`'s `OpConstructPayload` codegen (correct tag,
    payload written into a DIFFERENT alternative's struct field) and drives it
    through interpreter/-O0/-O3 comparison. It was BUILT AND RUN FOR REAL.

Measured result: no disagreement on any of the five axes. The reason is structural,
not a construction error. A payload-carrying return's `Outcome.Value` is on BOTH
engines the alternative's compile-time-known TAG NAME — `cgen`'s `returnLiteral`
is a literal string baked into the generated C at emission time and never read
back from the runtime struct, and `interp`'s `value.String()` resolves through the
tag field, never the payload bytes (D-12-26: `interp` has no byte layout at all).
The current grammar (`analyzePayloadArm`, D-12-05) only ever permits a bare-value
match arm's result to be an alternative NAME, never raw payload content — so no
execution document this phase can produce carries payload bytes in its terminal
outcome, and a wrong-slot write is invisible to every axis by construction.

Per D-12-41/D-11-36, plan 05 escalated this as a DEFECT IN THE CRITERION rather
than quietly downgrading to a weaker assertion. `TestPayloadSlotSwapMutationKilled`
passes by measuring and pinning that absence — a genuine passing regression test
in `TestC03PeerDeriveOriginFactsOpCallGapStillOpen`'s gap-pinning tradition, not
a false claim that the mutation was caught. Plan 12-07 Task 3 additionally closed
WR-02, so the control can no longer pass VACUOUSLY: it now asserts a wrong-slot
write was actually injected.

gap — not the finding's merit — is what `12-VERIFICATION.md` routed to you.

hazard CR-01 named is now refused outright by plans 12-06 and 12-07. What D-12-43
concerns is whether a runtime VALUE divergence for a wrong-slot write can be
