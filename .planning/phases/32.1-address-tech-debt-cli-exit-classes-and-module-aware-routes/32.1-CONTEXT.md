# Phase 32.1: Address tech debt: CLI exit classes and module-aware routes - Context

**Gathered:** 2026-10-12
**Status:** Ready for planning

<domain>
## Phase Boundary

This is an inserted M006 tech-debt closure. Its source is `.planning/M006-MILESTONE-AUDIT.md` (status `tech_debt`, commit 558cbbae). It makes every public CLI route report its outcome under the DX-17 single exit-class table, and it makes the module boundary of each route explicit and pinned. It closes three groups of debt:

1. **Exit classes.**
   - `run` on an entry whose parameter it cannot bind stops being a false exit 3 "operational failure".
   - A `ByteView` entry stops passing `check` when no engine can run it (29 WR-02).
   - The interpreter's defect result on the fixture route matches native (29 WR-03).
2. **Module-aware routes.** Every route is classified as either module-aware or refusing imports. The refusal set is named once and pinned by the route audit, and the usage text lists every dispatched route.
3. **Latent divergence.** The execution peer's entry rule is aligned with D-01 `main` precedence, and an armed control covers unpruned input.

Because these are code changes, the final M006 revision moves. The phase therefore ends by **re-taking the EVD-15 hosted receipts** at its final revision.

The phase adds no new language capability and no new input grammar.

### `run` with an unbindable entry parameter (DX-17; todo folded)
- **D-01:** `run --engine=interpreter|native` on a program whose entry has a parameter that `run` cannot bind refuses **before any engine or clang work**.
  - Exit **64** (`exitcode.Usage`), status `usage`, code **`tool.run_input_required`**.
  - Both engines give the same code.
  - The hint is static text pointing to `build` + `app run -- INPUT`.
  - The output never echoes the path, the source or any parameter name.
  - Precedent: `tool.unsupported_engine` (also usage/64), and sysexits EX_USAGE, which the project already uses.
  - **Reversibility:** costly. It re-pins the Phase 28 exit-class manifest rows and published CLI exit behavior.
- **D-02:** Exit 2 is rejected because the program is valid (`check` exits 0), and exit 2 must keep meaning "source judged invalid".
  - Exit 65 (`AppInputRefused`) is rejected because it is the published `app run` contract and must not be repurposed.
  - No new exit constant.
- **D-03:** The trigger condition is exactly "the entry parameter has no binding in `run`'s input supplier": `interpreterInputs` (session.go ~1218) returns `!ok`.
  - `run` today *does* execute Byte, Buffer and data-match mains through fixture inputs. These must keep running, so the todo's statement that `run` "cannot execute any admitted program" is too strong.
  - The check sits after admission and entry resolution, so source refusals still win and exit 2.
- **D-04:** Deliberate re-pins happen in the same change, each with a dated comment:
  - `cmd/schway/main_phase30_test.go` (~83) and `cmd/schway/main_phase29_test.go` (~52).
  - **Only** the `session_phase28_manifest_test.go` rows whose run failure is the unbound-parameter case. Verify each row's cause before flipping it.
- **D-05:** Armed controls that must stay unchanged:
  - A source refusal on `run` still exits 2 with its checker/validator code (e.g. the `core.origin_omitted` rows).
  - Genuine tool failures still exit 3: the cut fixtures in `native_test.go` (~1507, ~1518) and `session_phase16_production_paths_test.go` (~35), plus `native.tool_missing`.
- **D-06:** A new test runs `run` on a `fn main(n: U64)` program with both engines. It asserts exit 64 and `tool.run_input_required`, identical JSON across engines, **zero runner/clang invocations** (the runner stub counts calls), and no path in the output.
- **D-07:** Docs and records:
  - Add a `tool.run_input_required` row to the README exit table.
  - Replace the "Known limits" bullet at `examples/checksum/README.md:146` with a pointer to the code.
  - Move the todo to done.
  - The Phase 31 deferral of `run --engine=X FILE -- INPUT` stays open (see Deferred).

### Phase 29 review findings (29 WR-02, WR-03; the rest dispositioned)
- **D-08 (WR-02):** `check` refuses a `ByteView` parameter **on the resolved entry function only**.
  - It reuses `check.unexecutable_shape` (exit 2, repair kind `use_executable_shape`). Detail text names the supported entry inputs. No new code name.
  - **[synthesis]** The researcher also proposed refusing on *exported* functions. That is rejected: the exported `adler32` library function takes a `ByteView`, so the rule must be entry-only.
  - Required negative controls:
    - `examples/checksum/adler32.schway`, `examples/checksum/checksum.schway`, `examples/checksum/adler32_cli.schway`, `examples/checksum/adler_low.schway` and `examples/phase29/adler32_fixture.schway` still check clean.
    - Non-entry `ByteView` loop functions still check.
  - **Seam with D-01:** check runs first, so a `ByteView` main exits 2 at check and never reaches the D-01 `run` refusal. A U64 main passes check and gets D-01's exit 64. The two do not overlap.
- **D-09 (WR-03):** Widen the interpreter's fixture-route predicate (`isByteIndexDefect`, interp.go ~318/~370) so that **any defect terminal** with live fixture resources yields a defect Execution. That means OpBytesAt, checked-add overflow, remainder by zero and user `defect`. The Execution carries exit 65 and the native stderr text, restoring differential parity with native.
  - A normal return or typed failure with live resources still returns the hard error.
  - Each defect kind gets a test against native exit and stderr, plus a negative control that a normal return with a live owner is still refused.

### Module-aware routes (MOD-03 boundary; usage todo folded)
- **D-11:** **No route becomes newly module-aware in this phase.**
  - `evidence`, `evidence --validate`, `interface export|core|check`, `query` and `explain` keep the named refusal `module.imports_not_loaded` (exit 2) on import-bearing sources.
  - Making `interface` module-aware *is* per-module interface artifacts (MOD-01, MOD-02, B1/DX-06, out of scope).
  - Making `evidence` module-aware needs a multi-module evidence schema and a validator that reloads the module set, which is a feature.
  - **Reversibility:** reversible.
- **D-12:** The module-aware set is named **once**, as a shared constant, and three things derive from it:
  1. The refusal text at check.go ~102 and ~2349. Today it says "(check, run, build, app verify, debug-map)". It must name exactly the module-aware set and say that the refusing routes are single-file by design.
  2. The usage text.
  3. The route audit.
- **D-13:** Extend `TestPhase32PublicRouteAudit` (`phase32RouteRows`, `cmd/schway/main_phase32_routes_test.go`) with a module-awareness classification, either `module-aware` or `refuses-imports`.
  - The audit fails if a dispatched route has no classification.
  - For every `refuses-imports` route, it runs an import-bearing fixture and requires `module.imports_not_loaded`.
  - The existing `SetIgnoreUnloadedImportsForTest` armed control is kept.
- **D-14 (folded todo):** The usage text lists every dispatched route, including `stats` and `build SOURCE --output ARTIFACT --manifest MANIFEST` (both flag orders), plus the module-aware set.
  - Empty `phase32UsageOmissions` in the same change.
  - Move the todo to done.

### Entry resolver parity (DX-18 latent)
- **D-15:** `executionpeer.resolveEntry` (executionpeer.go ~272) stays an **independent implementation** with its own adjacency and in-degree, and no import of `callgraph` or session. Its *rule* aligns with Phase 28 D-01:
  - First pass: exactly one function named `main` is chosen; more than one refuses.
  - Otherwise it falls through to the existing root and closure tiebreak, unchanged.
  - Option A, where the peer consumes the session-resolved entry, is rejected because it destroys independence.
  - This refines the 28 D-19 wording ("keeps its copy of the tiebreak"); the tiebreak copy is kept.
  - Before coding, confirm that `core.Function.Name` is populated in the peer's input.
- **D-16:** Add an armed control `unpruned-main-precedence-parity` in `executionpeer_phase28_internal_test.go`:
  1. The input is unpruned. It has `main` calling `shared`, and a dead root calling `shared` plus a chain `a`→`b`, so the dead root's closure is larger than `main`'s.
  2. `callgraph.EntryFunction` and the peer both return `main`.
  3. A test-local `legacyResolveEntry`, a copy of the old rule, returns the dead root. That proves the control is not vacuous.
  4. Parity subtests:
     - Two `main` functions refuse.
     - A tie with no `main` still refuses `entry_ambiguous`; the existing test at ~104 is kept.
     - A tie that includes `main` resolves to `main`.
  5. A corpus assertion: wherever the session rule returns an entry, the unpruned and pruned programs resolve identically.

<specifics>
## Specific Ideas

- Prior art for D-01: `cargo run` and `go run` refuse an unrunnable target with a named message before executing anything, and never report it as a runtime failure.
- Prior art for D-15: CompCert-style translation validation, where the validator is an independent implementation of the *same* specification. Divergent specs turn a differential check into noise.
- Adversarial scope notes: three items look like debt but are new capabilities, and are excluded. They are WR-01 gating (a new trust tier), the WR-04 build-tag refactor, and a module-aware `interface` (MOD-01/MOD-02).

</specifics>
