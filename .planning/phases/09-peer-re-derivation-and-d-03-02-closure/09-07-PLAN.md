## Planner findings the executor must not re-derive

- **There is one algorithm with two callers, not two laws** (D-09-07).
  `computeLoanLastUses` (`check.go:3743`) calls the SAME `loanLivenessFixpoint`,
  fed synthetic `shadow:place:parameter` / `shadow:place:<n>` operations built
  straight from `ast.LinearBody` before any `core.Function` exists, plus a
  permanent zero-value `interproceduralSummaryTable{}`. A task that says "delete
  the intraprocedural loan-liveness algorithm" is describing the wrong thing.
- **Only TWO of the five `ownership.*` codes depend on that timing index**
  (D-09-47, verified): `ownership.move_while_borrowed` (`check.go:2176`, `:3392`,
  gated by `activeLoans[source.place.ID]` being non-empty, seeded from
  `expiringLoans[loan.lastUse]` populated at each borrow binding using
  `loanUses[index]`) and `ownership.borrow_conflict` (via
  `conflictingLoan(activeLoans[...])`, the same `activeLoans` set). The other
  three fire from immediate per-binding facts — `use_after_move` from
  `!source.initialized`, `borrow_requires_share` / `transfer_requires_take` from
  `hasTypeAbility`. A diff touching `!source.initialized` or any `hasTypeAbility`
  call is scope creep past what OWN-09 requires.
- **`core.Program.Functions` is a SLICE** (`core/core.go:19`), verified, so
  post-assembly iteration order is deterministic by declaration order. If it were
  a map, the ordering hazard would be nondeterministic across runs rather than
  merely different-from-before.
- **`Code + Span + Causes` fold into the diagnostic `ID`** — `Error()` marshals
  `{Schema, Code, Span, Causes}` and SHA-256-hashes it
  (`diagnostic/diagnostic.go:96-112`). This is why emission-order changes are
  observable in a published identifier.
- **The two call sites the restructure retires** are `analyzeArmBody`
  (`check.go:2069`, consuming at `:2074`) and `analyzeStraightLine`
  (`check.go:3280`, consuming at `:3287`). This plan reads them; plan 09-09
  changes them.

must contain a task that settles it rather than an assumption that inherits it.

The mechanism of the risk: `ownership.move_while_borrowed` currently PREVENTS a
move by refusing it inline. Removing that inline gate means the move proceeds
during lowering — marking the place moved, i.e. `source.initialized = false` —

function has both a `move_while_borrowed`-triggering move AND a subsequent
access to the SAME place that would trip `ownership.use_after_move`, then today's
inline refusal short-circuits before that access is reached, while a deferred
refusal would let lowering proceed far enough to ALSO trip `use_after_move` —
producing two errors where one existed, and changing which one is reported first.

**(a) Enumerate, do not sample.** Write
`TestUseAfterMoveUnchangedByDeferredMoveWhileBorrowed`. Enumerate EVERY `.lang`
fixture under `testdata/` where `ownership.move_while_borrowed` currently fires —
the corpus is ~58 programs averaging ~28 lines, so enumeration is bounded work,
which is exactly why this is settled by enumeration rather than by argument. For
each, assert the property that must hold after the restructure: that the function
containing the offending move has no subsequent access to the moved place that
would independently raise `ownership.use_after_move` if lowering proceeded past
the move.

Express that as a positive, checkable assertion over the fixture's own
`ast.LinearBody` or its lowered `core.Function` — for each fixture, the set of
places read after the offending move's index, intersected with the moved place,
must be empty. If a fixture violates it, that fixture is the concrete instance of
the risk: record it by name in the SUMMARY, add it to an explicitly declared
exception set in the test with a stated expected post-restructure behavior, and
raise it as an agenda item for plan 09-08's mid-phase gate. Do NOT silently adjust
the property to make the fixture pass.
