<objective>
Expand the tracer's single direction into the full two-bit summary mechanism:
derive `UsesParam` from each function's own checked body exactly once, in
reverse postorder, memoized within the run and transitive through relays; consume
it through one added gate in `blockLoanLiveness`; and pin the two invariants that
make the cost claim true — program order, and no persistence.

Purpose: `UsesParam` is the bit no declared field can supply (D-08-01 —
`core.FunctionSignature` was built incapable of carrying it), and its transitivity
is what makes the memo load-bearing rather than decorative. This plan is the
mechanism the whole phase's cost gate later measures.

Output: a body-derived, memoized, transitive `UsesParam`; the backward `OpCall`
gate; and the program-order and never-persisted invariants under test.
</objective>

    - The same relay pointed at a `usesParam == false` callee reports `usesParam == false`.
    - A three-deep chain (`caller → relay → leaf`) propagates the leaf's bit to the caller.

  <action>
Add `deriveFunctionUsesParam(function core.Function, summaries interproceduralSummaryTable) (bool, int)`
and call it from `buildInterproceduralSummaries` inside the existing reverse-postorder
loop, storing the result into the entry alongside `returnsBorrowOfParam`.

**Derivation rule, over `function.Linear.Operations` in program order.** Seed a
set of parameter-derived place IDs with `function.Parameter.ID`. Walk the
operations once, in order; an operation whose `SourceID` is in the set adds its
`TargetID` to the set (this is the program-order propagation D-08-11 measures —
one forward pass suffices only because the stream is in program order). The
function's `usesParam` is true when any operation whose `SourceID` is in the
parameter-derived set is either:
  - not an `OpCall` and not the function's own terminating `OpReturn` (a plain
    read of the parameter or of something derived from it), or
  - an `OpCall` whose `CalleeID` resolves in `summaries` to an entry with
    `usesParam == true`. Because the loop runs in reverse postorder, that entry
    is already final — this consult is a map read, never a re-walk of the
    callee's body, which is the whole of OWN-06's consumption reading.
An `OpCall` to a callee not present in `summaries` counts as `usesParam == true`:
absence is the refusing direction, never the permitting one.

**Traversal shape.** Whatever auxiliary walk the derivation needs must be
iterative with an explicit stack from the start (D-08-19a) — never a
self-calling `var walk func(...)` closure. Depth is program-controlled.

**Work counting.** Count one unit per operation inspected and one per set
insertion, returning the total, and fold it into
`buildInterproceduralSummaries`'s returned work. This is the deterministic
counter 08-05's cost gate consumes; it must never be a flat per-function unit.

**Doc comment.** State, at the derivation, that operations must arrive in
program order and why: spike S-006 iteration 5 measured 4.0 work units per
operation flat from k=8 to k=512 in program order, against 12.4 → 767.0 per
operation for the same chain reversed — a 192x penalty at k=512, quadratic in
body length. Note that this is an invariant Phase 08 INHERITS from today's
emission order, not a property of the mechanism: any future pass that reorders
operations before summary derivation hands the bound back.

**Tests.** Add `TestSummaryDerivationIsOnePassPerFunction`: build a diamond-shaped
synthetic `core.Program` (one caller, two relays, one shared leaf), instrument
the derivation with a per-function invocation counter, and assert each function
is derived exactly once even though the leaf has two callers. Add table-driven
cases covering every behaviour listed above, including the two-hop chain.
