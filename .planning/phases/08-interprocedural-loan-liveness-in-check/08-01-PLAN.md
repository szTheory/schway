## Planner assumptions (unresolved edge probes, surfaced not dropped)

The deterministic edge probe returned four `unresolved` edges over OWN-06 and
EFF-02. Two are resolved by 08-CONTEXT.md and lifted into `must_haves` in the
plans that own them; two are genuine planner assumptions and are recorded here:

1. **OWN-06 / boundary — RESOLVED by CONTEXT.** The bound is
   `loanLivenessBoundFactor × len(blocks) × distinctLoanCount` with the named
   refusal `check.loan_liveness_bound_exceeded` (D-08-13/D-08-14, code string
   ratified at this plan's Task 1). Owned by plan 08-04.
2. **OWN-06 / precision — PLANNER ASSUMPTION.** The bound is computed in Go
   `int` arithmetic. At the sizes this language can express (58 programs, ~28
   lines, one block per arm) `blocks × loans` cannot approach `math.MaxInt`, so
   no overflow contract is specified and none is tested. **If a later milestone
   makes block or loan counts program-controlled, this assumption must be
   re-opened before the bound is trusted.** Recorded in 08-04's own assumption
   note, not silently omitted.
3. **EFF-02 / boundary — RESOLVED by CONTEXT.** Growth exponent fitted against
   OPERATION count, bounded at ≤ 1.2 inclusive, with a ratio-stability tripwire
   at ≤ 15% between size S and 4S. Owned by plan 08-05.
4. **EFF-02 / precision — PLANNER ASSUMPTION, made concrete.** `QLT02BudgetRow.ValueOrBound`
   is `int64`, so a fractional exponent cannot be stored without a schema change
   (forbidden by D-08-24's reasoning). The plan therefore stores the bound in
   **milli-units**: `value_or_bound: 1200`, `unit: "milliexponent"`, and the gate
   compares `int64(math.Round(exponent*1000)) > 1200`. Rounding is `math.Round`
   (half away from zero); the ≤ 1.2 boundary stays inclusive; a fitted 1.2004
   passes and a fitted 1.2006 fails. **This tie-breaking contract is a planner
   decision, not a CONTEXT lock**, and 08-05 must pin it with a boundary test.
