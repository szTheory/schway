## Summary

The whole W1 fix is much smaller than the context implies. The conformance C for `examples/sum_to_n.schway` already selects a **dedicated recorder variant** because `emitProgram` computes `trackEventOccurrences := hasCyclicScalarCopy(program)` (`cgen_program.go:878`) and passes it into `emitEventSupportSchema2` (`cgen_program.go:912`). That helper is a pure function of the admitted program: it is true only when some block lies on a CFG cycle and contains a non-loan U64/Bool `Copy`. Those copies are the only per-iteration event source in a scalar body (`emitProgramScalarFunction` has exactly two `schway_record_event` sites: `value.copied` at line 2681 and `function.returned` at 2742). So the existing flag is exactly the D-27.3-12 gate, no new detection code is needed, and in the accepted corpus only `examples/sum_to_n.schway` selects it (66 programs emit conformance C, 27 refuse, 1 tracked; measured in scratch).

The fix is one line in one branch of `emitEventSupportSchema2` (the `else if trackOccurrences` branch, i.e. the non-application tracked recorder at `cgen.go:~750`): replace `if (schway_event_count >= SCHWAY_EVENT_CAPACITY) return 0;` with a block that writes a fixed stderr line and calls `exit(69)`. All `... abort();` call sites stay untouched (they remain reachable only through the `occurrence == UINT64_MAX` return-0 path). Loop-free conformance C and all application C are byte-identical by construction. I compiled the patched `sum_to_n` conformance C with `-std=c17 -Wall -Wextra -Werror -pedantic` at -O0 and -O3: n = 14 exits 0 with a 5,589-byte document, n = 15 and n = 100 exit 69 with empty stdout and stderr `schway: event capacity exhausted`. The unpatched C exits 134 (SIGABRT).

For the runner, the choice is the failure-path per-input re-run in `session_app_verify.go` (not a widened `native.Pair`/`Result`). `Runner.Run` has about 25 call sites across mismatch, mutation, phase-5 and run-native code; a per-pair "exhausted" marker would fail open for every caller that does not check it. Keeping `Run` batch-fail-closed with a new named `ToolError` code protects all of them, and app verify recovers per-case results only in its own failure path. One finding changes a test in D-27.3-10: `schway run --engine=native` cannot reach a loop program at all today (see Pitfall 6 / Open Question 1). W4 is a doc edit plus a static test; `git check-ignore` is already spawnable through `testsupport.RunCLIErr` using `git -C <root>`, exactly as `TestPhase27GuideContract` already does for `git rev-parse`.

**Primary recommendation:** Edit one recorder branch in `cgen.go` to `exit(69)` with `schway: event capacity exhausted\n`; teach `native.Runner.Run` to map exactly that exit status plus stderr to `ToolError{Code: "native.event_capacity_exhausted"}`; have `VerifyApplicationCases` recover per-case results by re-running per input only when that code appears; pin loop-free bytes with a pre-fix conformance golden whose only allow-listed change is `examples/sum_to_n.schway`; move the guide outputs under `.schway/phase27/` with a static `git check-ignore` test.

### Pattern 1: Named capacity exit in the tracked non-application recorder
**What:** Replace only the capacity guard of the `else if trackOccurrences` recorder. Quoted from the current source [VERIFIED: internal/compiler/cgen/cgen.go, `emitEventSupportSchema2` second recorder branch]:

```
  if (schway_event_count >= SCHWAY_EVENT_CAPACITY) return 0;
```
**Proposed replacement (compiled and executed in scratch):**
```
  if (schway_event_count >= SCHWAY_EVENT_CAPACITY) { fputs("schway: event capacity exhausted\n", stderr); exit(69); }
```
`<stdlib.h>` and `<stdio.h>` are always included by `emitProgram` (`#include <stdio.h>\n#include <stdlib.h>`), so no include change is needed. Edit only the Go string literal of the tracked non-application branch. The other three recorder branches (application tracked, application untracked, plain untracked) are not touched.
**When to use:** Execution/conformance shell, program has a cyclic scalar copy.

### Pattern 2: Runner adjudication by wait status plus stderr
**What:** Extend `exitAdjudication` (`native.go:711-714`, currently `Signaled`, `Signal`) with `Exited bool` and `ExitCode int` from `status.Exited()` / `status.ExitStatus()`, still via `ProcessState.Sys().(syscall.WaitStatus)` (D-04-24 forbids a shell's encoding, not a wait-status code). In the `runErr != nil` branch (`native.go:~619`), before the `expectedAbort` logic, add:

```go
if known && adjudication.Exited && adjudication.ExitCode == EventCapacityExitStatus &&
	string(runStderr.bytes()) == EventCapacityStderr {
	return Result{}, &ToolError{Code: CodeEventCapacityExhausted, Err: fmt.Errorf("generated C exceeded its static event capacity at %s", optimization)}
}
```
with exported constants in `native` (`CodeEventCapacityExhausted = "native.event_capacity_exhausted"`, `EventCapacityExitStatus = 69`, `EventCapacityStderr = "schway: event capacity exhausted\n"`). Because it keys on a normal exit, not a signal, the `ExpectDefect` SIGABRT path is unchanged by construction. Place it ahead of the existing `if !expectedAbort` block so a defect-expecting runner still names capacity.

### Pattern 3: App-verify level runner with failure-path recovery
```go
// session_app_verify.go (new, unexported; not in the Phase 16 emitter inventory)
type appVerifyLevel struct {
	Pairs     []native.Pair // len == len(inputs); zero Execution where Exhausted[i]
	Exhausted []bool        // len == len(inputs)
}

func isEventCapacityExhausted(err error) bool // errors.As(*native.ToolError) && Code == native.CodeEventCapacityExhausted

func runAppVerifyLevel(ctx context.Context, runner native.Runner, cSource, level string, inputs []string) (appVerifyLevel, error)
```
Behavior: try one batch `runner.Run(ctx, cSource, level, inputs)`. If `err == nil && len(Pairs) == len(inputs)` return it. If `isEventCapacityExhausted(err)`, loop inputs, `runner.Run(ctx, cSource, level, []string{input})` each: success sets `Pairs[i]`; capacity code sets `Exhausted[i]`; any other error returns `(appVerifyLevel{}, thatError)` so the caller applies the existing whole-set `markReplayFailures` plus batch error path. Any non-capacity batch error returns immediately, unchanged.

In `VerifyApplicationCases` (current lines ~330-345): call it for -O0 on `validInputs`; build the -O3 input subset from the non-exhausted inputs and call it again (so non-exhausted cases still run at both levels, D-27.3-06). For each exhausted case set `Engines = {"interpreter": interpreted[idx]}` only: no O0 or O3 entry and no placeholder, so no engine-agreement claim is made for an exhausted case (D-27.3-08); fully compared cases keep their three entries, then:

```go
if interp.Outcome.Kind == expected.Kind && interp.Outcome.Value == expected.Value {
	Status = ReplayStatusUnsupported
	Diagnostic = "native.event_capacity_exhausted: generated C exceeded its static event capacity at -O0; outcome not established, not a mismatch"
} else {
	Status = ReplayStatusFail
	Diagnostic = fmt.Sprintf("interpreter produced %s:%s, expected %s:%s", ...)  // true mismatch is never relabeled (D-27.3-08)
}
```
Name the real level (`-O0`, or `-O3` if only O3 exhausts, which should be impossible since the event count is optimizer-independent; handle it anyway).

## Common Pitfalls

### Pitfall 1: Moving loop-free C bytes
**What goes wrong:** Any edit outside the tracked non-application recorder branch changes `testdata/phase1/generated.golden.c`, `phase2/owned_transfer.golden.c` or `phase5/restrict_borrow.golden.c`, the substring assertions, or the application hashes.
**Why:** Four recorder branches are string literals in one function.
**How to avoid:** Edit exactly one literal. The new identity golden proves it for the whole accepted corpus; `TestPhase272AcceptedCorpusByteIdentity` proves the application shell.
**Warning signs:** Any golden `.c` diff; `TestPhase272AcceptedCorpusByteIdentity` failing.

### Pitfall 2: Generating the golden after the fix
**What goes wrong:** The golden would encode the fix, proving nothing.
**How to avoid:** First task commits the identity test plus golden at the pre-fix HEAD, with `SCHWAY_PHASE273_GOLDEN_REVISION=$(git rev-parse HEAD)` supplied by the caller (no subprocess in the test). The expected-change entry (`examples/sum_to_n.schway`) is asserted stronger than "differs": reverse the one-line substitution in the observed C and require the golden hash, proving the diff is exactly that line.

### Pitfall 3: Phase 16 emitter inventory drift
**What goes wrong:** `TestPhase16PublicEmitterConsumerInventory` keys `cgen.Emit`/`EmitNative` calls (aliased, plus unqualified inside package cgen) by `file:Func:line`. Registered non-test rows: `evidence/evidence.go:Emit:211`, `session/session.go:EmitNative:3071`, `session_phase5.go:EmitNative:26`, `session_phase5_mismatch.go:EmitNative:284` and `583`, `session_phase6_verify.go:EmitNative:318`, `session_phase7.go:Emit:501`, plus many rows in existing cgen test files [VERIFIED: testdata/phase16/public-emitter-consumers.json lines 5-81, 253, 272, 336, 345, 349, 366, 370].
**How to avoid:** (a) Put new session helpers in `session_app_verify.go`. (b) Do not edit `session.go` above line 3071 or `session_phase5.go` above line 26. (c) In new tests obtain conformance C through `session.Phase16ControlNativeC` (not a `cgen.` call), as `cgen_phase27_evidence_test.go` already imports `session`. (d) Put new cgen tests in a new file; never insert lines above registered calls in `cgen_program_test.go`, `cgen_names_test.go`, `cgen_n1_convergence_test.go`. If a direct `cgen.EmitNative` call is unavoidable, add a registry row with classification `admitted-dynamic-schema2`.

### Pitfall 4: Meta-tests scanning `.planning` docs
**What goes wrong:** Groundedness scans markdown **table rows** only; a backtick span starting with `go test`, `git `, `grep`, etc. inside a table cell must parse and resolve (27.1 failed hosted CI on this). Fenced blocks and prose are not scanned [VERIFIED: 27.2-RESEARCH.md lines 255-257].
**How to avoid:** In PLAN/VALIDATION tables name tests without command spans; put runnable commands in fenced blocks. Never write a bare race command in a table. Finalize `27.3-VALIDATION.md` (`status` not `draft`) before dispatch. Run the meta-tests before any planning-doc commit.

### Pitfall 5: Reports over 64 KiB
**What goes wrong:** `writeApplicationVerificationReport` rejects reports over `MaxReplayCasesBytes` (64 KiB). Each n = 14 `sum_to_n` case carries three 5.6 KB execution documents (about 17 KB).
**How to avoid:** Tests use at most a few n ~ 14 cases (mixed {14, 15} is about 23 KB: one full case plus interpreter-only evidence for 15). Keeping only the interpreter in `Engines` for exhausted cases is also what keeps this bounded.

### Pitfall 6: `schway run --engine=native` cannot reach a loop program today
**What goes wrong:** `runNative` takes its inputs from `interpreterInputs` (`session.go:1234-1266`), which returns `(nil, false)` for any linear entry whose parameter is not `Byte` or `Buffer`. A scalar CFG loop body requires a `U64` entry, so `schway run --engine=native examples/sum_to_n.schway` fails with `os.ErrInvalid` before running anything. I reproduced it: the output is `native.tool_failure`, not `run_signaled` and not a signal [VERIFIED: ran the built binary on examples/sum_to_n.schway]. The D-27.3-10 bullet "`schway run --engine=native` on a loop program past capacity reports the named code" therefore cannot be tested end-to-end through the CLI.

### Pitfall 7: Exit status 69 vs defect terminals
