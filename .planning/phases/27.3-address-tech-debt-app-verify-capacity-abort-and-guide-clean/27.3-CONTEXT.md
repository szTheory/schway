**Gathered:** 2026-10-10

<domain>
## Phase Boundary

Close two fail-closed milestone-audit warnings without adding capability:

- **W1.** `schway app verify` on `examples/sum_to_n.schway` aborts with
  `native.run_signaled` (SIGABRT) for n >= 15 instead of naming the cause.
  Root cause (verified by discuss-phase research, reproduced at 6854e4d):
  `invocationEventCapacity` (`internal/compiler/cgen/cgen_program.go:176`) sums
  `len(Linear.Operations)` once per preflight node, under the false comment
  "Every supported whole-program body is straight-line". `sum_to_n` is a scalar
  CFG body with a `while` loop. Its conformance C gets
  `SCHWAY_EVENT_CAPACITY 15u`, but it records one `value.copied` per iteration
  plus one `function.returned`, so n = 14 records 15 events and n = 15 records 16.
  The conformance/execution shell (`Phase16ControlNativeC` → `cgen.EmitNative`
  → `emitProgram(program, true)`) uses the `return 0` recorder variants
  (`cgen.go:755`, `:759`), and every call site is followed by `abort()`
  (`cgen_program.go:1660`, `1734`–`1808`, and scalar bodies at ~`2681`/`2742`).
  The runner reports any signal as `native.run_signaled` (`native/native.go:623`),
  returns one batch error, and app verify then marks every valid case
  "-O0 generated-C execution failed" and skips -O3
  (`session_app_verify.go` ~330–345). The same shell serves
  `schway run --engine=native`, so it has the same defect on loop programs.
  The application shell (`schway build` / `app run`) is **not** affected. It
  already uses the overflow-flag recorder (`cgen.go:753`, `:757`) and the named
  `capacity_exhausted` capture (`cgen_program.go:1059`, `:1069`;
  `native.evidence_capacity_exhausted`).
- **W4.** The "Clean-checkout run" block in `examples/phase27/README.md:14-23`
  writes `./phase27-fizzbuzz`, `./phase27-sum`, their
  `*.schway-build.json` sidecars (`native_app.go:117`) and `./*.actual` into the
  repo root. These are not ignored (`.gitignore` covers only `/schway`,
  `/.schway/`, `/.gsd/`, `risklane-state.json`). A later
  `scripts/verify-phase27.sh` receipt is therefore rejected `tree_not_clean`:
  `git status --porcelain` counts untracked files (`verify-phase27.sh:42`,
  `check-phase27-receipts.sh:83,90`).

Out of scope: making `sum_to_n` verify across its full accepted domain
(n <= 1000) through app verify; W2 and W3; R1b; the D-27.1-10 deferrals
(F3/F4/F5); any validator change; any new syntax or capability.
</domain>

<decisions>
## Implementation Decisions

Decisions are synthesized from four parallel advisor researches (fix depth,
report surface, byte identity, guide output location), each fanned out across
compiler/runtime, security/fail-closed, verification-integrity, CLI/DX, C/systems,
test and CI lenses with an adversarial pass. Per the user's instruction, the
recommendations were adopted directly rather than put to a per-area vote.

### W1 fix depth
- **D-27.3-01:** Fail closed with a **named, C-emitted** capacity outcome. Event
  capacity overflow in the execution/conformance shell must no longer reach
  `abort()`. The generated C reports it explicitly: a distinct non-signal exit
  status plus a fixed stderr line. The native runner adjudicates that as a
  named tool code, `native.event_capacity_exhausted`, never `native.run_signaled`.
  Inferring capacity from SIGABRT in Go was rejected: SIGABRT also comes from
  occurrence overflow (`cgen.go:753`), output write failure (`cgen.go:734`) and
  defect terminals, so the name must be emitted, not guessed. —
  **Reversibility:** costly — it adds a runner tool code and a shell exit-status
  contract that tests and reports will key on.
- **D-27.3-02:** Exit status and stderr wording are at Claude's/research's
  discretion, with these constraints. The status must not collide with
  64 (usage), 65 (bad input/defect) or 74 (output write failure). It should follow
  the sysexits convention those codes already use. The `ExpectDefect` SIGABRT
  path (D-04-15) must stay exactly as it is.
- **D-27.3-03:** Do **not** raise or loop-scale the static capacity in this
  phase. A fixed loop allowance (e.g. 1,001 or 4,096 events) is a guess: the
  `n < 1001` guard is not statically analyzable in general, unguarded loops stay
  unbounded, `schema2ExecutionDocumentSize` would no longer match runtime, and the
  recorder's schema-2 occurrence scan is O(n²). The honest result is that
  app verify of `sum_to_n` verifies n <= 14 and names exhaustion above that.
  The 16 MiB document ceiling would allow about 45k events (measured
  ~372 B/event; n = 1000 ≈ 372 KB), so loop-aware capacity is feasible later.
  It is deferred (see `<deferred>`).
- **D-27.3-04:** Do not change `invocationEventCapacity`'s arithmetic. It also
  feeds the application shell, and a change would move accepted-corpus hashes.
  Correct its false "straight-line" comment to state the actual contract
  (static per-activation count; loop bodies may exceed it and are caught at
  runtime by the named outcome). Comments do not change emitted bytes.
- **D-27.3-05:** Do not refuse loop-bearing programs up front in app verify.
  That would regress a route that works today for small n and remove the only
  loop-bearing public example from the peer route, against EVD-12's intent.

### W1 report surface
- **D-27.3-06:** An exhausted case is reported **per case**. Other cases in the
  same set still run and report normally at both -O0 and -O3. Preferred
  mechanism: the runner returns per-pair outcomes for the named
  exhaustion instead of one batch error. If that widens the runner API too much,
  app verify re-runs the affected batch one input at a time, in the failure path
  only. The planner picks after reading `native.go` ~560–625.
- **D-27.3-07:** Status `unsupported` (existing enum, `session_app_verify.go:33-35`)
  with a diagnostic that starts with the tool code, e.g.
  `native.event_capacity_exhausted: generated C exceeded its static event capacity at -O0; outcome not established, not a mismatch`.
  The diagnostic names the opt level. No new status value and no
  `lang.app-verification/1` schema bump; adding an enum to a `/1` schema was
  rejected for compatibility. `unsupported` already means "not established
  within the verifier's bounds" and is non-passing (`Verified=false`).
- **D-27.3-08:** Guard against masking. The case gets `unsupported` only when
  the interpreter completed and its outcome equals the expected value. If the
  interpreter disagrees with the expected value, the case stays `fail`
  (a true mismatch is never relabeled). The interpreter has no event bound
  (`interp.go:46`, only `MaxCallDepth = 128`). No engine-agreement claim is
  made for an exhausted case, and its interpreter evidence may be kept in `Engines`.
- **D-27.3-09:** The CLI exit class is unchanged. `schway app verify` still exits 3
  (`exitOperational`, `cmd/schway/main.go:305-310`) whenever `!Verified`.
  Optional: one stderr summary line counting capacity-exhausted cases. Scripts
  keep their contract.
- **D-27.3-10:** Tests, all focused and red→green per D-27.1-14 and D-27.2-06:
  - `sum_to_n` n = 14 passes on all three engines.
  - n = 15 reports `unsupported` with the `native.event_capacity_exhausted`
    diagnostic, `Verified=false`, and no signal anywhere in the report.
  - A mixed set {14, 15} has 14 `pass` and 15 `unsupported`.
  - CLI exit is 3.
  - A wrong-expected control stays `fail` (extend
    `TestPhase22AppVerifyWrongExpectedAnswerControl`).
  - A non-capacity runner error (missing clang, `native.timeout`) is still an
    operational error.
  - `schway run --engine=native` on a loop program past capacity reports the named
    code, not `native.run_signaled`.
  - The red run is recorded before the fix (`native.run_signaled ... abort trap`).

### W1 byte identity / blast radius
- **D-27.3-11:** The application shell (`EmitApplication`, `programApplicationShell`)
  stays byte-identical. `TestPhase272AcceptedCorpusByteIdentity` and its golden
  (`testdata/phase272/accepted-corpus-hashes.json`, application C plus core only)
  must pass unchanged and must **not** be regenerated. Phase 27 and 27.1 receipts
  are not regenerated (sources and fixtures unchanged; the README is not pinned
  by any receipt, `verify-phase27.sh:44-61`).
- **D-27.3-12:** In the execution/conformance shell, gate the new recorder and
  epilogue so that **loop-free programs emit exactly today's bytes**. This keeps
  `testdata/phase1/generated.golden.c`, `testdata/phase2/owned_transfer.golden.c`
  and the recorder substring assertions (`cgen_test.go:495-533`,
  `cgen_program_test.go:1585-1591`) unchanged. Only programs whose bodies can
  exceed the static count (scalar CFG bodies with a back edge) get the new code
  path. Vary only the event-support selection (as `emitEventSupportSchema2`
  already does with flags); share all function-body emitters, so app verify never
  passes on C that differs from what `build` would run except in the
  recorder. — **Reversibility:** costly — the gating condition becomes part of
  the emitter contract that the goldens rely on.
- **D-27.3-13:** Pin D-27.3-12 with a new identity test following the 27.2
  golden discipline. Conformance (`EmitNative`) C hashes for the accepted corpus
  are generated at the **pre-fix** revision, written only behind an explicit
  env flag plus a required revision env var (no subprocess, per the
  TestSourceNeverSpawnsUnboundedProcesses lesson from 27.2). Loop-free entries
  must match exactly. Loop-bearing entries that are expected to change are listed
  in an explicit allow-list. No existing golden is regenerated.
- **D-27.3-14:** If the change touches a public emitter entry point or adds an
  emitter call site, register it in the Phase 16 emitter inventory
  (`session_phase16_emitter_inventory_test.go`). Prefer no new public emitter.

### W4 guide output location
- **D-27.3-15:** The guide writes every output under the already-ignored
  `.schway/phase27/`. A `mkdir -p .schway/phase27` line comes before the builds,
  because `native_app.go:182` `MkdirTemp(outputDirectory, …)` needs the
  directory to exist. Artifacts, sidecars and `.actual` files all land there.
  No `.gitignore` change: broad globs like `/*.actual` were rejected because
  they can hide real untracked source. `go build -o ./schway` stays (`/schway` is
  ignored), and the guide strings that `TestPhase27GuideContract` requires stay.
- **D-27.3-16:** Enforcement is a static, always-on, clang-free test. Every
  `--output` target and redirect target in the clean-checkout block is under
  `.schway/`, and `git check-ignore` confirms that path is ignored, or the test
  asserts `/.schway/` stays in `.gitignore` if spawning git is unwanted. An
  executed, clang-gated run of the block in a temp git repo is at Claude's
  discretion. Do it only if the bounded spawn path supports a working
  directory without a new unbounded spawn; `testsupport.RunCLIErr` has no Dir
  parameter today. The test must never run guide commands in the real tree.

### Evidence and process (carried forward)
- **D-27.3-17:** Locally, run only focused `go test <pkgs> -run '<named>' -count=1`.
  Run the session meta-tests (`Inventory|Groundedness|Reconciliation|ValidationLifecycle`)
  before any planning-doc commit. Full and race suites run only in one hosted
  two-host `ci.yml` `workflow_dispatch` at the final SHA, after explicit user
  approval for each push and dispatch. Never force-push. No push while a hosted
  run is in progress.
- **D-27.3-18:** Validators (corevalidate, originvalidate, executionpeer, interp)
  stay unchanged; `git diff --stat <pre-fix> -- <validator dirs>` must be empty.
  No new dependencies; go.mod and go.sum are unchanged.
- **D-27.3-19:** Record-keeping: write `27.3-HOST-EVIDENCE.md` in the
  27.1/27.2 format, with "Claims and limits". Not claimed: full-domain app verify
  of `sum_to_n`, receipt regeneration, new requirement completion. The milestone
  audit's W1/W4 rows are updated by the next `/gsd-audit-milestone`, not by this
  phase. Stage explicit paths only, commit with plain git, and never commit
  `.gitkeep`, `.gsd/` or `.planning/milestone.lock`.
