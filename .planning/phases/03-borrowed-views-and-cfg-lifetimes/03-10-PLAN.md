<assumption_delta_decision>
The `assumption-delta` probe fired with a `pluralization` signal on ROADMAP SC3's phrase
"field/alternative origins", and here the signal is materially correct rather than noise:
this defect IS a singular-to-plural transition. `RecomputeOrigin` was written against the
assumption *"a function has one return operation"*; the truth is *"a function has one return
operation per arm"*.

**Noun that is now primary:** the SET of per-`OpReturn` origin derivations for a function —
`[]ReturnOrigin` — not "the return origin".

**Decision: promote.** `RecomputeOriginPerReturn(function core.Function) []ReturnOrigin`
becomes the primary derivation and the only place a backward walk is performed. The existing
exported `RecomputeOrigin(function) (paths []string, access string, ok bool)` is retained
with its signature unchanged, but is reimplemented as a pure conservative COMBINER over that
slice — the singular answer becomes the degenerate one-element case of the plural one.

**Rationale:** the alternative (`add-alongside` — keeping the single-return walk primary and
bolting a multi-arm path beside it) leaves two derivations able to disagree about the same
function, which is precisely the failure mode that produced this third gap-closure round.
Only one backward walk may exist in the package after this plan; Task 03-10-02's grep gate
enforces that by counting backward-walk sites.
</assumption_delta_decision>

<combination_law>
## The conservative combination law — decided here, not left to the executor

Let `derived` be the subset of `RecomputeOriginPerReturn`'s results whose backward walk
reached `function.Parameter.ID` through at least one `core.OpBorrowShared` or
`core.OpBorrowExclusive` hop (each element's own first-seen-hop-wins rule is 03-08's fix and
is preserved verbatim, per return).

1. `derived` empty (every return is owned, or every chain breaks) → `RecomputeOrigin` returns
   `(nil, "", false)`. Byte-identical to today for `branch_view.lang`, `borrowed_view.lang`,
   and every owned straight-line function.
2. `derived` non-empty, all elements agree on access mode → paths are the ordered union of
   the elements' paths, access is that agreed mode, `ok` is true. Byte-identical to today for
   a one-return function.
3. `derived` non-empty, elements DISAGREE on access mode → paths are the ordered union,
   access is the exported sentinel `AccessConflicting` (string value `conflicting`), `ok` is
   true. This is the clause 03-VERIFICATION.md demands: neither arm wins.

Consequences in `ValidatePublished`, which is otherwise unchanged (first-problem-only,
same branch order):
- No declared origin + `ok` true (any case 2 or 3) → `core.origin_omitted`, Detail naming the
  function ID, the union paths, and the derived access (which reads as the sentinel in case 3).
- Declared origin + case 3 → the declared access is `shared` or `exclusive`, neither of which
  equals the sentinel, so `core.origin_access_mismatch` fires. Its Detail must name the
  sentinel value so a reader can tell a conflict apart from an ordinary single-mode mismatch.
- Declared origin whose `Access` is not one of `shared` or `exclusive` → refused with
  `core.origin_access_mismatch` BEFORE the recomputed comparison, so a mutated summary cannot
  declare the sentinel and match a conflicting recomputation.
</combination_law>
