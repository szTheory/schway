<objective>
Build a genuinely different second decision procedure for loan liveness, prove it is load-bearing by mutation, and make the property generators reach the shapes that matter.

Purpose: ROADMAP criterion 1 requires borrow conflicts to be accepted or rejected identically by the core checker and a bounded path oracle. D-09 makes the mutation kill mandatory, because Phase 2's ownership oracle encoded the same wrong law as production and the differential agreed on the wrong answer. D-10 makes the generator's reachable space a written artifact, because two Phase 2 blockers hid behind generators that never reached the hard case.
Output: a bounded path-oracle package, a mutation-killed differential, a path-count cap, and generators that reach branching and exclusive shapes.
</objective>

  <name>Task 03-05-01: Bounded acyclic path enumeration as a third decision procedure</name>
  <files>internal/compiler/pathoracle/pathoracle.go, internal/compiler/pathoracle/pathoracle_test.go</files>
  <behavior>
    - Given a checked `core.Function`, the oracle enumerates every acyclic path from the entry block to the return, in a deterministic order.
    - Each path is linearized into a straight-line operation sequence and decided by the retained straight-line last-use logic, which is order-independent of the production fixpoint.
    - Per-loan endpoints are assembled from the per-path answers: a loan that dies at different positions on different paths yields an edge endpoint at the divergence; one that dies at the same position on every path yields a point endpoint.
    - A path whose linearization lacks a terminal ending for a live loan is a hard failure, not a normalized repair.
    - The oracle reads only the core artifact; it imports no production liveness function and no source text.
  </behavior>
  <action>Create `internal/compiler/pathoracle` and write its tests first, beginning with a test asserting the package imports neither `check` nor `corevalidate` nor `ast`. Implement exhaustive acyclic path expansion over the declared blocks and edges — a different mechanism class from the production monotone fixpoint, per pitfall 2 in the research: an oracle written as the production dataflow twice lets a bug in the shared mental model escape both. Reuse the straight-line last-use logic retained in 03-03 as the per-path linearization step, which is legitimate because it is already independently oracle-tested and is no longer the production CFG answer. Add the late terminal guard the spike requires: if a linearized path leaves a loan live at the return with no endpoint, fail loudly rather than letting the normalizer invent one, because a silent repair masks exactly the missing-endpoint fault this oracle exists to catch. Assemble endpoints across paths and compare against the production `LoanEndpoints` with whole-value equality. Write a doc comment stating both procedures explicitly and arguing that neither is obtainable from the other by renaming, in the style of `check_test.go:254-263`.</action>
