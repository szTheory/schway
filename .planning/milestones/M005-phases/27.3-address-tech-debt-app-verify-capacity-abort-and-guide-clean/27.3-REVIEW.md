# Phase 27.3: Code Review Report

**Reviewed:** 2026-10-10
**Depth:** standard
**Files Reviewed:** 12

## Summary

The core fail-closed design holds. The runner maps only exit 69 plus exact stderr to the capacity code. Re-runs happen only after that code. Index bookkeeping (`o3Positions` / `o3Slot`) is consistent, including the empty -O3 batch. An exhausted case is `unsupported` only when the interpreter outcome equals the expected outcome, and `fail` otherwise. I found no blockers. The warnings are about masking a cross-level divergence and about test and documentation robustness.

## Warnings

### WR-01: Exhaustion at one level masks a possible O0/O3 divergence

**File:** `internal/compiler/session/session_app_verify.go:337-349, 353-368`
**Issue:** If an input exhausts capacity at only one level, the case is marked exhausted. This is unsupported when the interpreter matches expected. The other level's completed evidence is discarded, and no cross-level comparison is made. Event counts should be identical across -O0 and -O3. Exhaustion at only one level therefore signals miscompilation or undefined behavior, which is exactly what this verifier exists to catch, yet it is reported as a benign `unsupported` with a diagnostic saying "not a mismatch". Exhaustion at -O0 also skips the -O3 run entirely.
**Fix:** Track exhaustion per level (`o0Exhausted`, `o3Exhausted`). When exactly one level exhausts and the other completed, report `fail` with a diagnostic such as "capacity exhausted at -O3 only". Report `unsupported` only when both levels exhaust. To establish that, run the input at -O3 even when -O0 exhausted.

### WR-02: Guide static test is bypassable and depends on a git checkout

**File:** `internal/compiler/session/session_phase273_docs_test.go:68-70, 135-150`
**Issue:** `phase273TargetAllowed` is a prefix check. A path such as `./.schway/../leak` passes the prefix check. The target parser also misses `>>`, `-o=path`, `--output=path`, and `tee`. When `git check-ignore` exits 128 (tarball or source-archive checkout, or no git on PATH), the `default:` case calls `t.Fatalf`, which turns an environmental condition into a failure. In addition, the `cmp` read-side files are not checked, though that is fine.
**Fix:** Run `path.Clean` on each target before the prefix check. Also parse `>>` and `--output=`. Treat an exit of 128 or a missing git as `t.Skip`, or rely on the `.gitignore` text check.

### WR-03: Boundary test hardcodes the capacity edge

**File:** `cmd/schway/main_test.go:~846-870` (`TestPhase273AppVerifyCapacityCLI`); `cmd/schway/main_test.go:~585-602`
**Issue:** The test assumes n=14 completes and n=15 exhausts for `examples/sum_to_n.schway`. If the static capacity arithmetic changes, or someone edits the example, this fails with an opaque message. The comment in `invocationEventCapacity` says the arithmetic "must not change without moving accepted-corpus hashes". The boundary is therefore coupled to the example source and to the generated-C event count, and nothing in the test derives it.
**Fix:** Compute the boundary from the emitted capacity, or assert a named invariant (n=0 passes and a large n exhausts). Alternatively, document the coupling in the test with a pointer to the corpus-hash golden.

## Info

### IN-01: Re-run path recompiles per input

**File:** `internal/compiler/session/session_app_verify.go:505-514`
**Issue:** After a batch capacity failure, each input re-runs through `runner.Run`. `BuildCache` is nil, so clang compiles once per input per level. The recovery path is correct, but it multiplies compile time and the per-run timeouts. Performance is out of scope for v1, so this is noted only.
**Fix:** Optional. Keep the compiled binary across single re-runs, or document the cost.

### IN-02: Capacity guard is only partially converted

**File:** `internal/compiler/cgen/cgen.go:752-760`
**Issue:** Only the `trackOccurrences && !applicationEvidence` recorder exits with 69. The non-tracked, non-application variant still does `return 0` at overflow. The `occurrence == UINT64_MAX` path also still returns 0. These paths are presumably unreachable or handled by callers, but the identity tests do not prove it.
**Fix:** Add a comment at the other variants stating why they cannot reach exhaustion, or convert them consistently.
